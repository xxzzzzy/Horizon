### [Rendering huge pull requests in the GitHub Copilot app](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/) ⭐️ 8.0/10

GitHub engineers rebuilt the pull request view in the GitHub Copilot app to render extremely large diffs without performance degradation, validating the design against an open-source PR with 2,200 files, over a million changed lines, and more than 400 inline review comments. The starting point was an imperative, recycled code-row renderer backed by typed-array offset math and a backend-owned diff document streamed structure-first, which works because every code line has a predictable height computed up front under an &quot;all heights known before paint&quot; contract. Comments break that contract because their height depends on markdown wrapping, expandable &lt;details&gt; blocks, inline reply composers, reactions, edit mode, and asynchronously loaded images, so the team split the document into two independent geometry domains: a deterministic code height computed by prefix sum, plus a separate index of dynamic block heights that are estimated first and corrected lazily. Each dynamic block is identified by a stable key anchored to a file, line and side rather than a pixel coordinate, carries a fingerprint of the inputs that affect its height \(content, whether a details element is open, whether a composer is active\), and records the width bucket it was last measured at so ordinary resizes do not invalidate every measurement in the document. To avoid the feedback loop that one ResizeObserver per block would create, the shipped design replaces per-block observers with a single idle- and scroll-gated measurement pass scoped to roughly 2,400 pixels around the viewport, so that only nearby blocks are remeasured at any moment and distant blocks continue riding their cached estimates.

rss · GitHub Blog · Sep 23, 18:29

**「Background」** For a diff viewer to scroll smoothly across hundreds of thousands of lines, only a small window of rows can be in the DOM at once, so virtualizers reuse a fixed pool of row elements and compute positions from a height table; this works cleanly when every row has the same predictable height, as is the case for source code lines at a fixed font size. Inline review comments violate that assumption because their height is only knowable after rendering, and changes such as an expanding details element, an opened reply box, a suggested-change diff, or a late-loading image can shift the content&\#x27;s height after first paint, which is what forces a PR viewer&\#x27;s architecture to handle comments as a fundamentally different kind of content than code rows.

**「Impact」** Developers reviewing very large pull requests in the GitHub Copilot app can now open and scroll PRs with millions of changed lines and hundreds of inline comments without the scroll jumps and layout thrash that arose when comment heights were remeasured on the hot path, since comment resizes no longer force the deterministic code geometry to be rebuilt and only affect measurements within roughly 2,400 pixels of the viewport.

### [European report warns of rising orbital collision risk from satellite growth](https://arstechnica.com/space/2026/09/there-are-now-17000-satellites-in-orbit-and-growing-should-we-be-concerned/) ⭐️ 7.0/10

A new European report warns that rapid growth in satellite constellations—now approximately 17,000 active satellites according to CelesTrak, up from about 1,000 in 2013—is substantially raising the risk of orbital collisions and Kessler syndrome scenarios. SpaceX&\#x27;s Starlink constellation accounts for roughly 11,000 of those satellites, with thousands more planned, while Amazon and multiple Chinese internet constellations are also expanding rapidly. Looking ahead, planned orbital data centers could eventually involve hundreds of thousands of satellites. The report frames the long-standing Kessler syndrome concept—first proposed by NASA scientists Donald Kessler and Burton Cour-Palais nearly half a century ago—in a new quantitative context, raising questions about the long-term sustainability of low-Earth orbit. The article surveys both pessimistic and optimistic outlooks depending on whose analysis is consulted.

rss · Ars Technica · Sep 23, 11:00

**「Background」** The Kessler syndrome, first proposed by NASA scientists Donald Kessler and Burton Cour-Palais in 1978, describes a scenario in which collisions between objects in orbit generate debris that triggers further collisions, potentially rendering orbital regions unusable for generations. The risk is directly tied to the number of satellites and debris objects in orbit; the European Space Agency estimates that around 140 million debris items larger than one millimeter currently litter Earth&\#x27;s orbit. The concept gained broad public attention through the 2013 film Gravity, but its plausibility has grown as the active satellite population has risen from roughly 1,000 in 2013 to about 17,000 today, driven largely by large broadband constellations such as SpaceX&\#x27;s Starlink.

**「Impact」** The roughly 17-fold increase in active satellites since 2013—now about 17,000 according to CelesTrak, with SpaceX&\#x27;s Starlink alone contributing approximately 11,000—has materially raised the probability of cascading in-orbit collisions that could render low-Earth orbit regions difficult or impossible to use for commercial broadband, Earth observation, and scientific missions. The risk is amplified by the lack of a unified debris-mitigation framework, as evidenced by conflicting US timelines \(the FCC has moved to a 5-year post-mission disposal rule while some legacy provisions remained at 25 years\), leaving operators like SpaceX, Rocket Lab, and the Satellite Industry Association to navigate duplicative and inconsistent regulatory authority.
